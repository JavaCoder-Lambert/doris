# 3.0.8 → 4.1.4 升级评估说明

核查日期：2026-09-11。本文用于开发、测试和运维共同评估升级；没有执行生产变更。目标是 **Linux x86_64**，服务器发行版、版本及 CPU 指令集仍待确认。

**可以继续准备 4.1.4 修复包与隔离演练，但现有证据不足以批准生产直接从 3.0.8 升至 4.1.4，也不能承诺直接降回 3.0.8。** 官方跨版本矩阵尚未给出这条具体路径的兼容结论；本次官方 4.1.4 ARM64 包还复现了单字符串 NULL-safe Join 错误结果。修复源码、构建包验证与生产升级验收必须分别记录。

| 本 fork 修复包 | 以 4.1.4 为基础，回补单字符串 NULL key 与 RPC 回调/附件生命周期修复；源码锁定 `8048d149bd8264ce72c919ace2d6319aebe0597d` | 对应代码的 11 项 focused ASAN 单测通过；最终包摘要与运行验收仍待完成 |

版本身份依据见 [精确版本比较](comparison-3.0.8.md)及 [Apache 官方 4.1.4 Release](https://github.com/apache/doris/releases/tag/4.1.4-rc04)。tag 名带 `rc04`，不能单凭这个后缀否定其正式 Release 身份。

本次隔离 ARM64 发行包实验中，初始 100 项 SQL 探针在 3.0.8 全部通过，4.1.4 为 80 通过、20 项结果错误；后续固定种子的 60 项扩展探针在 3.0.8 全部通过，4.1.4 为 32 通过、28 项结果错误。合计 **3.0.8 为 160/160 通过，原版 4.1.4 为 112 通过、48 项结果错误**。48 是不同查询/配置组合的失败次数，不是 48 个独立缺陷；六键合成查询两版均通过，未复现 BE crash。见 [修复与实验记录](4.1.4-null-safe-fix.md)及 [初始版本对照](null-safe-join-validation.md)。使用版本匹配的 4.1.4 官方回归框架，`--compile` 成功；`test_null_safe_eq_join_string_key` 在第一个 `minimal_left_join` 断言失败，预期 `(2,1)`，实际 `(2,NULL)`，suite 其余断言未运行。

该红测使用原版官方包，FE/BE 均报告 `doris-4.1.4-rc04-ad35a140c7f`。golden 与 suite 运行前后 SHA-256 一致，没有用实际错误结果生成预期。本任务 FE/BE 已停止并保留日志；停机产生的退出码 137/143 不作为测试 crash 证据。完整命令和原始证据在本地调查目录 `../doris-investigation-20260911/official-regression-4.1.4-baseline.md`，不随本仓库提交。

## 官方支持边界与升级路径

官方建议：补丁版本可直接升级；跨 minor 应分阶段，跨 major 前先到当前 major 的最新 minor。滚动顺序为 **BE → FE 非 Master → FE Master**。官方要求先检查副本及客户端重试，并在隔离环境验证元数据兼容性。每阶段只在节点状态和验证通过后继续。[Cluster Upgrade](https://doris.apache.org/docs/4.x/admin-manual/cluster-management/upgrade/)

截至核查日，官方 Version Notes 中 `3.0.x / 3.1.x / 4.0.x / 4.1.x` 的矩阵仍标为 TODO，跨版本单元格为空；这不是“不支持”的证明，也不是已确认兼容。major 升级可能改变元数据或数据格式，向后兼容不保证；minor 的向后兼容说明有“不使用新特性”的前提。因此，本次**未确认 3.0.8 → 4.1.4 的直接生产升级路径，也未锁定任何中间补丁版本**。应按官方分阶段原则，在代表性环境逐段验证后确定实际版本序列。[Version Notes](https://doris.apache.org/docs/4.x/features-architecture/versioning/)

部署模式必须先确认。存算分离模式另有 MetaService/Recycler 升级顺序，且官方禁止跨 minor/major 降级；Local 与 Cloud 模式不能作为原地升级过程相互切换。本说明的 BE/FE 顺序不能替代 Cloud 模式完整流程。[存算分离升级](https://doris.apache.org/docs/3.x/compute-storage-decoupled/upgrade/)

## 交付包和目标机器需确认的条件

| 项目 | 需要形成的记录 |
|---|---|
| 系统与架构 | Linux 发行版及版本、内核、`uname -m`、glibc/动态库情况；目前只确定目标为 x86_64 |
| CPU | 目标机器 AVX2 支持情况与包编译选项一致；不能用 ARM64 红测代替 x86_64 验证 |
| Java | FE/BE 所用 JDK 17 路径与版本；保留原配置，核对新脚本所需 JVM 参数 |
| 包身份 | 源码提交、补丁清单、构建环境、完整命令、包文件名、SHA-256、二进制架构与依赖检查 |
| 集群形态 | Local/Cloud、FE 角色与数量、BE 数量、表副本分配、磁盘余量、节点健康与持续导入任务 |
| 实际使用范围 | 驱动/连接器版本、Catalog/UDF、权限和现有拦截规则；只针对真实使用项验收 |

官方区分 x64 AVX2、x64 no-AVX2、ARM64 包；环境指南要求 3.0 及以后使用 Java 17，推荐 `17.0.10+`。[环境要求](https://doris.apache.org/docs/4.x/install/preparation/env-checking/)、[包架构说明](https://doris.apache.org/docs/4.x/features-architecture/versioning/)。4.1.4 的 [start_fe.sh](https://github.com/apache/doris/blob/ad35a140c7fd0b842f18c23300bac581f7d04326/bin/start_fe.sh#L306-L320) 更明确：JDK major 必须等于 17，且需要 `JAVA_OPTS_FOR_JDK_17`。不能把“17 或任意更高版”作为该脚本保证。

本机此前的 JDK 错误已解决：用命令级 `JAVA_HOME/JDK_17/PATH` 指向 Microsoft OpenJDK 17.0.19 后，4.1.4 回归框架编译和运行均越过 JDK 检查，默认全局 Java 8 未改。这个结论只证明本次测试工具链可用，不证明目标服务器配置已合格。

目标 OS 尚未提供，因此本文不给出发行版、glibc 最低值或“任意 Linux 可运行”的保证。验收还应对照官方检查项核对时间同步、文件句柄、内存映射、Swap/THP 和端口；具体调整由目标环境演练确定。[Operating System Checks](https://doris.apache.org/docs/4.x/install/preparation/os-checking/)

## 与查询结果直接相关的兼容检查

现有 `block_null_safe_equal` 规则需要单独核对。SQL 阻止规则保存在 FE 元数据中，4.1.4 会读取规则并重放创建、修改和删除日志；沿用原元数据升级不会仅因替换 FE/BE 二进制而自动撤销该规则。源码依据为 [Env 的规则加载/保存](../../fe/fe-core/src/main/java/org/apache/doris/catalog/Env.java)及 [EditLog 的规则重放](../../fe/fe-core/src/main/java/org/apache/doris/persist/EditLog.java)。即使引擎修复验证通过，SQL 仍可能先被这条规则拒绝；应由有权限的操作人员在各阶段用 `SHOW SQL_BLOCK_RULE FOR block_null_safe_equal;` 保存实际正则、Enable、Global，并另行核对非全局规则的用户绑定范围。是否调整保护规则，应在对应查询通过代表性环境验收后另行决定；本任务未读取或更改生产规则。

升级会运行默认变量迁移。4.1.4 的 [VariableMgr.java](https://github.com/apache/doris/blob/ad35a140c7fd0b842f18c23300bac581f7d04326/fe/fe-core/src/main/java/org/apache/doris/qe/VariableMgr.java#L1065-L1097) 显示：

| 触发条件 | 迁移内容 |
|---|---|
| `variable_version < 300` | 从 `sql_mode` 移除内部 DEFAULT 标记，并加入 `ONLY_FULL_GROUP_BY` |
| `variable_version < 400` | `enable_ansi_query_organization_behavior=false`；`enable_new_type_coercion_behavior=false`；`enable_sql_cache=true`；`enable_nereids_distribute_planner=true` |

这些是有条件的迁移逻辑，不能当成任意已有集群的实际值。每个升级阶段应保存迁移前后全局及新会话变量；已有连接、客户端初始化 SQL、已完成迁移的元数据都可能使实际设置不同。用相同输入和明确的会话设置比较完整行内容、类型、NULL 与空字符串、重复数，再记录计划和性能。

4.0 发布说明明确提醒 CAST、严格模式、浮点及日期行为调整可能影响已有查询和导入；应将业务实际使用的转换与边界数据纳入回归。[4.0.0 Release Notes](https://doris.apache.org/releases/v4.0/release-4.0.0/)。4.1 引入可显式选择的 Segment V3；本次修复验收期间建议保持既有存储特性，不同时启用新的格式，以减少回退演练变量。这是本次实施建议，不是对新格式降级兼容性的承诺。[4.1.0 Release Notes](https://doris.apache.org/releases/v4.1/release-4.1.0/)

4.1.4 发布说明还包含 CTE、聚合/Join nullability 和 RF 下推修正，说明升级会改变相关优化路径；它们不构成本次六键故障已修复的证明。[4.1.4 Release Notes](https://doris.apache.org/releases/v4.1/release-4.1.4/)。本次至少需验收：官方单字符串 suite、现有 100 项探针、完整业务 `q_raw` 与真实字段类型，以及多 BE 下的 RF/重启/导入并发场景。原查询缺失的上游 CTE、生产计划和崩溃栈仍限制历史事故归因。

## 备份、演练和回退

先备份 Master FE 元数据；目录以 `fe.conf` 的 `meta_dir` 为准。兼容测试使用备份副本、独立端口和不同 cluster ID，避免测试进程加入生产。升级保留原 `conf`、元数据和数据目录；按官方步骤备份并替换发行文件，`custom_lib` 保留，FE 证书目录需专门核对。副本 repair/balance 在升级期间按文档处理，结束或失败后恢复。[Cluster Upgrade](https://doris.apache.org/docs/4.x/admin-manual/cluster-management/upgrade/)

FE 元数据备份不代替表数据备份。对于存算一体模式，Doris 支持把库/表/分区快照写入 Repository，但 3.x 文档列出了不支持存算分离、MTMV 和使用 storage policy 的表等限制；恢复后还需处理 colocate 属性与动态分区。先盘点真实对象，逐项明确其恢复来源，不能用一个“全库备份完成”覆盖未支持对象。[3.x Backup and Restore](https://doris.apache.org/docs/3.x/admin-manual/data-admin/backup-restore/overview/)

若线上是 Cloud 模式，需覆盖 FE 与 MetaService/FDB 的元数据及数据存储。本次不提供未经版本验证的 Cloud 备份命令；例如官方同步 FE/FDB 备份 API 标明从 4.0.8 才支持，不能直接用于当前 3.0.8。[Meta Backup Action](https://doris.apache.org/docs/4.x/admin-manual/open-api/fe-http/meta-backup-action/)

建议由运维与业务共同验收以下恢复结果：

1. 备份任务实际完成，保存 Repository/label/timestamp、对象清单、版本和校验记录，并记录一致性时间点。
2. 在隔离环境实际恢复，核对表定义、分区、副本、行数、关键聚合、NULL/重复值以及未自动恢复的对象；仅能读取备份文件不算恢复验证。
3. 以升级前备份恢复旧版本环境，验证客户端重新连接、权限、查询和导入可用，测量实际恢复耗时。
4. 明确升级期间新增写入的保留/重放方案、允许丢失的数据窗口（RPO）和恢复时限（RTO）。跨版本失败时不能把旧二进制直接指向已被新版本写过的元数据，作为唯一回退计划。

第 3、4 项是本次交付的演练要求。它们并非声称 Apache 已保证任意 4.1.4 数据或元数据可降级至 3.0.8；未完成恢复演练前，不提供这种保证。
